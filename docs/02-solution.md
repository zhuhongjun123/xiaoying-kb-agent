# 02 方案

## 1 一条问题怎么走完

```text
question + history
        │
        ▼
   Decider        ① 看 State，选一个动作
  ─────────         mock（规则）或 llm（OpenAI 兼容），输出统一的 Action JSON
        │
        ▼
   Toolbox        ② 执行 search_docs / read_doc，可注入故障（第 N 次失败 / 全部失败）
        │
        ▼
   State          ③ 合并片段、记录检索指标、全文入册，同时重算冲突
        │
        ▼          ④ 预算是硬闸门：步数 / 工具次数，超了直接判 unfinished
   回到 ① 或 ⑤
        │
        ▼
   Guards         ⑤ 收尾：引用子串比对 + 数字绑定，不过就降级
```

四个动作，六个状态，两个上限。循环本身不含业务知识，业务判定全在 `guards.py` 和 `data/` 里。这样换模型只需要换 Decider，其他都不动。

## 2 动态决策

题目要求「至少实现一个模型选择动作、执行工具、观察结果、模型调整下一步或结束的循环」，并且明说「仅有固定条件分支、自动重试或预设决策日志，不视为完成」。这一节写清楚决策点在哪、可选动作有哪些、凭什么选。

### 2.1 决策点

每一轮循环只做一个判断：下一步干什么。判断的输入是当前 State，不是原始问题。

| State 里有什么 | 决策器据此判断 |
| --- | --- |
| 检索过没有、最高分多少、置信与否 | 要不要先检索、要不要换个说法再检索一次 |
| 已经看到哪些片段、哪些文档读了全文 | 证据够不够答，还缺不缺原文 |
| 有没有检出同主题的取值冲突、哪些参与文档还没读全文 | 是不是该去查证，还是已经查完了 |
| 已经失败过几次、失败的是哪个工具 | 重试、换策略，还是直接声明工具不可用 |
| 已用步数、已用工具次数 | 还有没有余量继续 |

### 2.2 动作空间

只有四个动作，多一个都会让决策变糊。

| 动作 | 参数 | 什么时候用 |
| --- | --- | --- |
| `search_docs` | `query`、`top_k` | 还没检索过，或上一轮置信度不够需要换词 |
| `read_doc` | `doc_id` | 检索看到两个数值不一致，要看优先级、适用范围、替代关系 |
| `ask_user` | `status`、`question`、`options` | 查证完仍然判不了，或者问题本身缺条件 |
| `finish` | `status`、`answer`、`citations`、`gaps`、`next_actions`、`basis` | 证据够答，或者明确答不了 |

输出是一个 JSON，两种决策器（规则策略、真实模型）产出的格式完全一样：

```jsonc
{"action": "search_docs", "args": {"query": "...", "top_k": 6}, "reason": "..."}
{"action": "read_doc",    "args": {"doc_id": "D02"},          "reason": "..."}
{"action": "ask_user",    "args": {"status": "conflict",
                                   "question": "应以哪份为准？",
                                   "options": ["D01", "D02"]}, "reason": "..."}
{"action": "finish",      "args": {"status": "answered|conflict|insufficient|out_of_scope",
                                   "answer": "...",                    // 可省
                                   "citations": [{"doc_id","quote"}],  // 可省
                                   "gaps": ["..."], "next_actions": ["..."],
                                   "basis": "..."},                    "reason": "..."}
```

`reason` 记的不是思维链，是这一步为什么选它。题目说不需要模型内部过程，但评审要能判断决策合不合理，所以每步都留一句。

`finish` 的 `answer` 可以不写。不写由代码用抽取式模板拼（规则策略走这条），写了就按模型原话，但必须过引用核验。这一步是我故意的：让「说什么」和「能不能说」分开，前者可以自由，后者必须过关。

### 2.3 三条实际走出来的路径

同一套循环在不同输入下走出的步数不一样，这正是它区别于固定流程的地方。

| 用例 | 实际路径 | 为什么分叉 |
| --- | --- | --- |
| C1 明确答案 | `search_docs` → `finish` | 一次检索命中单文档，同 key 只有一个取值，没有可查的东西 |
| C2 文档冲突 | `search_docs` → `read_doc D01` → `read_doc D02` → `ask_user` | 检索看到同一条款两个数值，先读全文找优先级和适用范围，读完两边都没有，才追问 |
| C7 工具全挂 | `search_docs`（失败）→ `search_docs`（改写后仍失败）→ `finish(insufficient)` | 第一次失败换词重试，第二次失败后不再消耗额度，直接说明工具不可用 |

C2 那四步里，第二、三步不是我预先写好的：「发现两个数值不一致 → 去读原文查证」这个判断依赖第一步的返回内容。`search_docs` 也不返回优先级和替代关系，想查证只能读全文，所以这两个动作没有别的替代方式。记录见 `examples/transcripts/C2.md`。

C7 的两次检索参数不同：第一次是原问题，第二次是改写后的说法（去掉疑问词、把「多久」换成「期限」），不是重复同一个请求。

### 2.4 预算中止

决策器每轮都能从 State 里读到还剩多少额度。真正拦下来的是循环，不是决策器：

```python
if state.steps >= max_steps:          → unfinished("达到步数上限 N")
if state.tool_calls >= max_tool_calls → unfinished("达到工具调用上限 N")  # 动作不执行
```

两个上限而不是一个：一次 search 可能带出好几次 read，只卡步数挡不住工具风暴。失败的工具调用照样计入额度，它消耗的也是真实配额。`unfinished` 不是空答案，会说明用了几步、几次调用、已经检索到哪些文档、为什么不给结论。C9 是 `max_steps=1` 造出来的。

## 3 冲突怎么判

冲突处理拆成三步：把条文变成可比较的断言、把比对范围限定在证据集内、按文档自身的效力声明消解。三步都由代码完成，模型不参与判定。

### 3.1 先把制度条文变成能比的东西

解析文档时，凡是 `- 键：值` 这种行都抽成一条 `Claim(doc_id, key, value, heading)`。9 份文档一共抽出 64 条。

抽出来之后，冲突判定就退化成数据结构问题：同一个 key 在不同文档里的取值是否一致。不需要语义理解，也不需要模型点头。

这么做还有一层好处。审核要点要求「替换文档内容，核对答案与动作是否改变」，判定走 claim，就自动满足；如果把规则写进提示词或写成 if 分支，改个数字结论不会变。

### 3.2 只在证据集内比对

比对范围不加限定，会出两类误报：

| 误报 | 成因 |
| --- | --- |
| 问「设备借用多久」，答成「调休 60 天」 | D01「起算时点：出差行程结束之日」和 D07「起算时点：加班发生之日」key 相同、值不同，被判成冲突。这个假冲突又恰好能被 D08 的取代声明消解，于是消解结果直接变成了答案 |
| 加了一份《差旅住宿标准》后，问住宿返回报销期限冲突 | 住宿问题把 D01、D02 一起拉进了证据集，而这两份之间确实有真冲突 |

所以证据集有两个限定：

1. 分数窗口。只保留分数 ≥ 最高分 × 0.5 的片段。检索必然带回弱相关结果，弱相关结果里的矛盾不该左右这次回答。
2. 主题聚焦。只保留和最强命中同主题（`doc.topic`）的片段。不同主题共用「起算时点」「适用范围」这类通用 key 是常态，跨主题比对必然是误报。

`test_no_conflict_across_topics` 和 `test_irrelevant_docs_excluded_from_evidence` 两条测试锁住这两个行为。

这里取宁漏不误。漏报的表现是两份文档各自作答，用户还能自己发现不一致；误报会给出一个不存在的矛盾，比不答更糟。

### 3.3 消解阶梯

`search_docs` 只返回片段和 `doc_id / 版本 / 生效日期`，不返回优先级、适用范围、替代关系。这三项在文档管理元数据里，只有 `read_doc` 才给。所以「看到两个数值不一致 → 去读原文查证」是一条真有必要的路径，不是为了把动作凑齐。

读到全文后按三级判：

| 级别 | 规则 | 输出的依据 |
| --- | --- | --- |
| 1 | 某份文档的 `supersedes` 指向组内另一份，该文档已生效（`effective_date ≤ 今天`），且剔除后取值唯一 | 「D08（v2.0，2026-06-01 生效）声明取代 D07，被取代文档的对应条款不再适用」 |
| 2 | 参与文档都显式声明了 `priority` 且不全相同（同样要求已生效） | 「取优先级最高者（D08，priority=2）」 |
| 3 | 以上都不成立 | 判为不可消解：列出双方取值，说明「有效期重叠、均未声明替代、无可用适用范围」，走 `conflict` 并追问 |

第一级里的「已生效」有用处。一份声明取代旧版的修订稿，如果生效日期还没到，拿它去消解等于用未来的制度管今天的报销。这种情况会在 `basis` 里写明「尚未到达（今天 X）」，然后退回第三级。

第三级还会核对 `scope`。两份文档的适用范围表述不同（「公司全体在职员工」和「总部及各分公司全体在职人员」），会写进查证结论，并说明两者都覆盖本次提问人群。这是把「查过了但判不了」讲清楚，而不是含糊带过。

判定权放在代码里，理由有三：结论要能复用和审计；模型给出的「D02 更具体」无法验证；换文档内容时模型行为不可预测，而审核要点要验的恰好是这一点。模型负责选动作和写叙述。

### 3.4 只消解一半也要说清楚

如果新增一份只取代 D01 的 D10，而 D02 仍和 D10 冲突，结论必须是部分消解后的冲突：D01 退出，D10 和 D02 继续对立。`test_partial_resolution_still_reports_conflict` 锁这个行为。真实企业里「改了一半」最常见，不能因为消解掉一组就宣布没事了。

## 4 引用怎么核

生成式模型最容易出的问题是编引用。两道确定性校验，思路来自我另一个项目 rs-research-copilot 的回查核验：

1. 子串比对。每条 `citation.quote` 去掉空白和行首列表符号后，必须是该文档全文的子串。差一个字就报「引用原文在 D01 中找不到」。
2. 数字绑定。答案里出现的每个数字都得能在引用原文里找到。`第 3.1 条`、`v1.2`、`2026-06-01`、`D08` 这类指称形态先剔掉，它们不是断言。

不过就降级，不放行：

```python
if problems and answer.status in ("answered", "conflict"):
    answer = Answer(status="insufficient", answer="已生成草稿，但引用无法与原文核对，故不作为答案输出：…")
```

模型可以写得很漂亮，引用对不上原文，这条答案就不交付。这比在末尾加一句「仅供参考」有用。

## 5 检索

9 份文档、35 个小节，这个规模上检索的目标不是最强，是错得能解释。

| 组件 | 做法 | 为什么 |
| --- | --- | --- |
| 分词 | 中文按字 bigram，英文和数字整词 | 不引 jieba。bigram 对短问句召回稳定，也不需要词典 |
| 排序 | BM25，k1=1.5，b=0.75 | 标准做法，一个 idf 就能把分数讲明白 |
| 标题加权 | 查询词命中小节标题时额外加 `1.5 × idf` | 修一个真实的排序 bug，见下 |
| 查询扩展 | `synonyms.json` 双向扩展（`报销`↔`报账/发票`，`期限`↔`时限/多久/几天`） | 「改写后的相似问题」能过关靠这个，C6 重试时换个说法也靠它 |
| 置信闸门 | top 分数 ≥ 0.9，且剔除泛词后至少命中 1 个内容 bigram | 只命中「公司」「什么」不算有内容。C3 判 out_of_scope 靠这条 |

标题命中要额外加权。不加权时，问「出差住宿一晚最多能报多少钱」，D01 的「目的与适用范围」会压过《差旅住宿标准》的「住宿上限」，因为那段的正文里恰好同时有出差、住宿、报销三个词。加 `1.5 × idf` 之后 D10 排到第一，`test_heading_boost_prefers_specific_section` 锁住这个行为。

不上向量检索的原因是这个规模下它只有成本：多一个依赖、多一层说不清的分数、评审还得联网装包。等库到几千份、或者问题和原文用词差得很远时再换，「混合检索 + RRF 融合」那时才划算。rs-copilot 用混合检索，因为它的库是整箱论文 PDF。

还有一条约束是证据形态：喂给模型的证据必须保持原文形态。多行片段一旦用 `" / "` 拼成一行，模型就会照着这个格式拼 quote，引用立刻对不上原文。所以状态渲染逐行输出，提示词里也写明 quote 必须是某一段连续原文。细节在 `docs/03-evaluation.md` §9.3。

## 6 技术取舍

| 决策点 | 采用 | 未采用 | 依据 |
| --- | --- | --- | --- |
| 语言与依赖 | 原生 Python，零第三方依赖 | LangGraph / ADK / AgentScope | 框架在这道题里不加分；评审要一条命令跑通；循环自己写才看得见决策点 |
| 模型通道 | 规则策略 + OpenAI 兼容，同一个 Action 契约 | 只做规则策略 | 没 key 也能验全链路，换真模型不改循环 |
| 规则策略的定位 | 明确标为规则，`provider` 字段如实写 | 当作模型使用 | 题目要求标明 mock 边界 |
| 冲突判定 | 确定性代码 | 模型判断 | 见 §3.3 |
| 回答方式 | 规则策略抽取式，模型生成式但过校验 | 全部生成式 | 抽取式不会编；生成式自由，代价是必须过闸门 |
| 追问 | 独立动作 `ask_user` | 答一个再加免责声明 | 参考实例要求「请求确认适用制度」 |
| 引用校验 | 子串 + 数字绑定，不过即降级 | 只提示不拦截 | 错误引用是关键缺陷，不能输出 |
| 检索 | BM25 + bigram + 标题加权 | 向量 / 混合检索 | 见 §5 |

## 7 和我另一个项目的对照

`rs-research-copilot` 做的是论文库问答，骨架和这里是一套，「检索 → 证据不足拒答 → 强制引用 → 回查核验」。差异来自两边对「矛盾」的定义不同。

| 环节 | rs-research-copilot | 本项目 |
| --- | --- | --- |
| 检索 | 向量 + BM25 + RRF 融合（库大、术语多） | BM25 + bigram + 标题加权（库小、要可解释） |
| 证据不足 | 语义门槛 + RRF 门槛 + 模型判断，拒答时给最接近的内容 | 分数门槛 + 内容词门槛，走 out_of_scope |
| 强制引用 | 提示词限定只许引用给定片段 | 同一约束，外加 `verify_answer` 硬校验 |
| 回查核验 | 数值断言拿去引用片段里做字符串比对 | 同一手法，再加「引用必须是原文子串」 |
| 额外能力 | 跨位置数值自洽审查（C1–C5） | 跨文档条款冲突检测与消解阶梯 |

论文库里矛盾是缺陷，要抓出来给人看；制度库里矛盾是业务事实，要暴露出来让人决策。所以这边多了消解阶梯和追问，那边只报不改。

## 8 故意没做的

- rerank 模型。9 份文档用不上，加了也没法解释分数。
- 多轮状态机。CLI 不存会话，靠调用方传 `history`。真实产品该有 session，但那是工程脚手架，不是这道题的重点。
- `compare_docs` 工具。读两次原文就能完成查证，多一个工具只是多一个决策分支。
- scope 子集自动消解。要做需要提问者的组织归属和岗位，这轮没有这个输入，硬推会造出错误结论，所以写进 `gaps` 让人确认。

## 9 技术栈与依赖

| 项 | 用了什么 | 说明 |
| --- | --- | --- |
| 语言 | Python 3.10+ | 用到 `Path.is_relative_to`、`datetime.date.fromisoformat` 这些 3.9 之后才齐的接口。本地实测 3.13 |
| 第三方依赖 | 无 | `requirements.txt` 里只有注释，说明为什么空 |
| Agent 框架 | 未使用 | LangGraph、ADK、AgentScope 都看过，不用：题目明说框架不加分，而且循环自己写出来才看得见决策点在哪 |
| 测试框架 | `unittest`（标准库） | 不引 pytest，评审机器上任何 Python 都能跑 |
| 模型调用 | 标准库 `urllib` | 直接 POST `/chat/completions`，不引 openai SDK，省一个依赖 |
| 其他标准库 | `argparse` `json` `math` `re` `pathlib` `dataclasses` `collections` `tempfile` `shutil` `datetime` | 检索、解析、CLI、测试全在这几个里面 |

题目的要求是「采用框架时，注明版本、使用的功能及其承担的职责」。这里没有框架可注。判定与循环分开写，是为了换决策器时不用动判定；真换成 LangGraph，只需把 `agent.py` 那个 while 循环改成 `StateGraph`，`guards.py` 和 `tools.py` 不动。
